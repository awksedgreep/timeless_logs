# TimelessLogs Full Performance Audit (i185)

**Date:** 2026-07-18
**Machine:** Intel Core Ultra 9 185H ("i185"), Linux, 22 schedulers
**Versions:** timeless_logs 1.4.18, ex_openzl 0.4.16, ezstd (zstd), Elixir 1.20.2 / OTP 29
**Container leg:** ghcr.io/awksedgreep/timeless-stack:0.6.6, fresh ephemeral container,
empty data dir, logs HTTP on host port 19428.

Two legs: the embedded mix-task bank (`timeless_logs.benchmark`,
`ingest_benchmark`, `search_benchmark`, `index_benchmark`) and a new
container HTTP workload (`bench/container_http_workload.exs`, auto-ramp
NDJSON ingest + concurrent LogsQL queries — added in this audit).

Prior baseline for comparison: `2026-03-12_ex_openzl_0.4.6.md` (Apple
Silicon Mac, ex_openzl 0.4.6) — different machine, so deltas are
directional only.

---

## Headline

- **HTTP ingest accept rate: 928K entries/s** at write p99 39ms, 0 errors —
  but this is an *accept* rate, not a durable rate. The server enqueues and
  204s; the disk pipeline lagged tens of millions of entries behind.
- **Finding 1 (critical): no ingest backpressure.** The container absorbed
  ~38.7M entries into buffer/mailbox memory and hit **32.4GB RSS**, still
  draining minutes after the client stopped. Unbounded `pending_batches`
  queue + `handle_cast` mailbox.
- **Finding 2 (critical): queries collapse under sustained ingest.**
  Query p50 went 81ms → 13.3s as blocks accumulated; above ~470K entries/s
  ingest, zero queries completed within a 15s window. Root cause is
  `count_total` defaulting to `true`, which forces every query to
  decompress **every** matching block (early-exit never halts:
  `if count_total or length(new_acc) < need do :cont`). The HTTP/LogsQL
  path never disables it.
- **Finding 3: compaction cannot keep up under load.** At the end of the
  run: 7,634 raw blocks vs 45 OpenZL blocks (~8GB raw on disk).
- OpenZL remains the right default at rest: 12.8x vs zstd's 10.0x,
  **38% faster decompression**, **36% faster scan queries**, and parallel
  compaction is now only **9.7% slower** than zstd on 22 cores (was 31%
  slower on the 10-core Mac).

**Parallel compaction (22 cores):** zstd 2.4M entries/s, OpenZL 2.2M
entries/s (**9.7% slower** — down from 31% slower on the 10-core Mac; the

### Search (1.13M entries, 1129 blocks, cold-ish)

| Query | Median | Matches |
|-------|-------:|--------:|
| level=error (indexed, ~2%) | 341ms | 6.7K |
| level=error, **limit 10** | **329ms** | 6.7K |
| level=error + service=api (intersection) | 304µs | 0 |
| message substring 'timeout' (scan) | 641ms | 2.8K |
| last 1 hour (time prune, ~0.6% of blocks) | 7.4ms | 6.8K |
| last 1 hour + level=error | 2.7ms | 46 |
| needle request_id | 46µs | 0 |
| all logs page 1 | 1.17s | 1.1M |

The tell is row 2: **limit 10 costs the same as unlimited** — `count_total`
forces the full block scan. Time-range pruning works beautifully (7.4ms
when ts_min/ts_max excludes 99.4% of blocks); the term index works when
selective. The failure mode is any query whose terms match many blocks.

Index overhead on disk: 0.4% (960KB for 240MB of blocks).

### Index ops (2K blocks, 200K entries, 18K terms, SQLite)

stats() 269µs; matching_block_ids 2.1–3.7ms; destructive retention ops ~10ms.
(The index benchmark crashed before this audit — it still read the pre-SQLite
ETS table; fixed in this commit.)

### What the flat write latency hides

- At bench end `/health` showed **3.77M entries on disk**; the client had
  sent **~38.7M**. The other ~35M sat in buffer shard mailboxes and
  `pending_batches` queues. Container RSS: **32.4GB**, CPU ~1400%
  draining for minutes afterward.
- During the drain, default `retention_max_size` (512MB) engaged and began
  deleting the oldest blocks — including all 45 compacted OpenZL blocks —
  while the backlog was still being written: a write-then-immediately-delete
  treadmill. Entries on disk went 38.7M → 2.55M as retention clamped to the
  cap.
- Compaction never got ahead: 7,634 raw vs 45 OpenZL blocks at peak.

So the honest container numbers are: **~930K entries/s HTTP accept**,
low-single-digit-ms enqueue latency, but a durable (write+index) pipeline
far below that, with no signal to the client and no bound on memory.

## Ranked findings

1. **No ingest backpressure (stability, critical).** `/insert/jsonline` →
   `TimelessLogs.ingest/1` → `handle_cast({:log_many, ...})` → unbounded
   buffer + unbounded `:queue` of pending batches. Overload converts
   directly to RSS (32GB observed). Recommend: bounded pending queue with
   an overload check at the HTTP layer (429 or synchronous degrade), the
   same lesson timeless_metrics learned with flush pressure.
2. **`count_total: true` default defeats early-exit (query perf,
   critical).** `do_query_parallel` collects every matching block whenever
   count_total is set; the HTTP path always uses the default. Recommend:
   default `count_total: false` on the LogsQL HTTP path (VictoriaLogs
   doesn't return exact totals on tail queries) and/or satisfy totals from
   per-block `entry_count` + term index instead of decompression when
   there are no post-filters. With early-exit actually halting, a
   `limit 100` desc tail query touches a handful of blocks.
3. **Compaction lags under load (storage + query perf).** Raw blocks are
   ~15x larger on disk and slower to scan; a 100:1 raw:compacted ratio
   compounds finding 2. Recommend larger compaction batches under
   pressure (the metrics raw-first work's age-gate + size-cap pattern
   applies here almost verbatim).
4. **Retention/backlog treadmill.** Size-based retention deleting blocks
   while the ingest backlog is still flushing wastes CPU on
   write-index-delete cycles. Draining shards could check retention
   pressure and shed queued batches instead of persisting doomed data.
5. **Shard count default.** `ingest_shard_count: 4` → 8 is +11% on 22
   cores (772K vs 697K entries/s). Worth a docs note or a
   `schedulers_online()`-derived default.
6. **`String.to_atom` on HTTP metadata keys** (http.ex `parse_log_line`).
   Unbounded client-controlled atom creation; atoms are never GC'd.
   Stability/DoS concern on public endpoints — switch to string keys or
   `String.to_existing_atom` with a fallback.
7. **Cosmetic:** `/select/logsql/stats` mixes seconds (`oldest_timestamp`)
   and microseconds (`newest_timestamp`); OpenZL level-1 first-call warmup
   anomaly in the level sweep.

## Cross-machine note (vs 2026-03-12 Mac baseline)

Single-thread compression on i185 runs ~0.5–0.7x the M-series Mac numbers
(zstd L3: 3.1M vs 6.3M entries/s; OpenZL L9: 562K vs 793K), consistent
with the metrics-side single-core observations. Parallel legs (compaction,
scan queries) close the gap with 22 cores. Rerun this file's two legs on
the Mac/faster-Intel with only the Machine line changed for a true bank.
